# Listen Graphic v2

## 播客结构化收听层产品设计方案

---

## 1. 产品定义

### 1.1 产品名称

**Listen Graphic**

### 1.2 一句话定义

一个面向长音频内容的**结构化收听层**：
在用户收听播客、访谈、语言节目等内容时，自动将对话内容转化为**可导航、可视化、可交互的逻辑结构**，帮助用户边听边理解，而不只是边听边看字幕。

### 1.3 核心价值主张

当前长音频产品大多解决的是：

* 听不清 → 转写字幕
* 听完忘了 → 摘要纪要
* 需要复盘 → 时间戳导航

但真正没有被解决的问题是：

> **长音频内容缺少“逻辑界面”。**

用户面对的是一条连续的声音流和一段一段的文本流，但很多访谈、知识类、讨论类节目，本质上并不是“线性听完即可”，而是包含：

* 观点与论据
* 因果链条
* 时间线叙事
* 多方分歧与共识
* 步骤流程与方法拆解

如果这些内容只以逐字稿或摘要呈现，用户仍然很难快速抓住全局结构。

**Listen Graphic 的目标不是再做一个转写/摘要工具，而是为长音频提供一个“结构化理解层”。**

---

## 2. 产品灵感与核心痛点

### 2.1 灵感来源

播客、访谈、语言类节目已经成为大量用户的日常内容消费形式。
但在很多高信息密度节目中，用户常常会遇到几个问题：

* 听的过程中很难抓住整体脉络
* 某个观点听懂了，但不知道它和前文后文的关系
* 多位嘉宾对同一话题的讨论容易混淆
* 听完后只记得零散片段，难以形成完整结构

尤其是知识型、访谈型节目，很多内容其实天然适合被表达成：

* 时间线
* 因果图
* 对比图
* 步骤图
* 结构图

而不是一味被压成“一级标题-二级标题-三级要点”的树形脑图。

### 2.2 核心初衷：拒绝无脑树状图

当前市场上大量“AI 思维导图/摘要工具”的问题在于：

* 只是把文本做层级拆分
* 没有真正识别语义关系
* 不区分辩论、因果、流程、时间线等不同逻辑
* 最终输出大量“无限分叉的大括号结构”

这会导致一种很强的表达失真：

> **不是所有知识内容都适合用树状图表达。**

Listen Graphic 的核心初衷是：

> **让图形服从语义，而不是让所有内容被迫服从同一种图。**

## 3. 产品定位与边界

### 3.1 产品定位

Listen Graphic 不是“播客摘要工具”，也不是“会议纪要工具的播客版”。

它更准确的定位是：

> **长音频的结构化收听层 / 逻辑侧边栏**

即在音频播放过程中，为用户提供一套伴随式、动态更新的结构界面，用于：

* 快速把握当前在讲什么
* 理解不同观点之间的关系
* 点击结构节点回跳音频片段
* 听后沉淀为可复用的知识材料

### 3.2 优先适配场景

第一阶段优先聚焦：

* 中文访谈类播客
* 知识型/分析型节目
* 财经 / 科技 / 职场 / 创业 /语言学习等高信息密度内容

这些内容具备：

* 逻辑关系较清晰
* 结构可提炼
* 用户有较强理解/复盘需求
* 相比泛娱乐内容更适合结构化表达

### 3.3 非优先场景

MVP 阶段不优先处理：

* 纯闲聊型节目
* 节奏极快、多人抢话极多的综艺式音频
* 强情绪表达而非结构表达的内容
* 对背景音乐/音效高度依赖的内容

---

## 4. 产品核心理念

### 4.1 从“声音流”到“逻辑界面”

产品不是试图替代音频本身，而是为音频增加一个“第二界面”：

* 左侧是声音流
* 右侧是逻辑结构
* 两者实时联动

用户不再只能靠记忆追踪一段长内容，而是能看到：

* 当前话题是什么
* 它属于哪种表达结构
* 谁在提出观点
* 谁在补充、反对、举例
* 当前内容在整期节目中的位置

### 4.2 从“单一图类型”到“多视图表达”

同一段内容不应被默认压成同一种图形。
产品应支持根据语义特征自动匹配最适合的视图，并允许用户手动切换。

### 4.3 从“模型直接画图”到“统一中间结构驱动视图”

产品的核心不应是让大模型直接输出 Mermaid/流程图代码。
更合理的架构是：

> **先把内容转为统一的结构化中间表示，再由前端渲染成不同图形。**

这样才能保证：

* 视图切换能力
* 节点交互能力
* 后续扩展能力
* 稳定性与可维护性

## 5. 用户价值与核心使用场景

### 5.1 核心用户

优先面向以下用户：

* 高频播客用户
* 学习型/知识型内容消费者
* 需要听后沉淀与复盘的用户
* 对信息结构和表达清晰度敏感的用户
* 愿意尝试 AI 辅助理解工具的深度用户

### 5.2 核心场景

#### 场景 A：边听边理解

用户在网页/插件中播放播客时，右侧同步显示节目当前内容的结构化图。
随着节目推进，图中节点逐步展开，高亮当前位置。

#### 场景 B：快速回看重点

用户听到某个观点没听清，可直接点击节点跳回对应时间点重听。

#### 场景 C：理解多嘉宾讨论

在多人访谈中，用户可以只看某一位嘉宾的观点，或只看分歧点/共识点。

#### 场景 D：听后复盘与沉淀

节目结束后，用户可导出：

* 结构图
* Markdown 笔记
* JSON 图谱
* PNG/SVG 图像

用于进入自己的知识库系统。

## 6. 核心产品差异化

### 6.1 核心差异不是“转写”，而是“结构理解”

市场上已有大量工具能完成：

* 音频转写
* 摘要纪要
* 字幕时间戳
* 关键词检索

Listen Graphic 的真正差异化在于：

1. **对内容逻辑关系的识别**
2. **不同语义模式对应不同视图**
3. **收听过程中的结构联动体验**
4. **面向播客/访谈场景的专门优化**

### 6.2 差异化方向总结

* 不是听后给你一个摘要，而是**听的时候给你一个结构**
* 不是一味画脑图，而是**让图形匹配内容**
* 不是只做静态结果，而是**做可导航、可交互的收听层**
* 不是泛会议工具，而是**聚焦长音频理解场景**

## 7. 产品形态

### 7.1 首阶段推荐形态

优先采用：

* **Web Demo / 桌面网页应用**（用于快速验证价值）
* 后续演进为 **Chrome/Edge 浏览器插件侧边栏**

### 7.2 为什么不一开始就重压插件

插件适合承载“边听边看”的核心体验，但不一定是最好的第一触点。
原因包括：

* 插件安装和授权步骤较重
* 音频抓取、页面适配和权限处理增加工程复杂度
* 初期应优先验证“结构化视图是否真的有用”，而不是先把集成做满

因此建议：

* **第一阶段先做最小 Demo**
* **验证用户是否真的愿意使用结构化收听界面**
* 再进入播放器联动和插件化

补充说明：

当前仓库里的插件实现也遵循这个原则，先收口到一条可运行的 side panel 主链路：`service worker -> content script -> AudioWorklet -> sidepanel`。`offscreen + tabCapture` 仍作为后续增强路线保留，而不是当前必须同步做满的部分。

### 7.3 中长期形态

* 浏览器插件
* 独立桌面端
* 创作者嵌入页
* 与知识管理产品的导出/连接能力

## 8. 产品架构总览

Listen Graphic 采用“三层分离”的架构设计：

### 8.1 三层架构

#### 第一层：音频理解层

负责：

* 音频获取
* ASR 转写
* 基础分段
* 说话人识别（可选）
* 时间戳同步

#### 第二层：结构抽取层

负责：

* 从文本中抽取统一的中间结构
* 识别节点、关系、说话人、时间锚点
* 合并 chunk 结果
* 输出标准化 JSON

#### 第三层：可视化与交互层

负责：

* 视图选择与渲染
* 节点高亮
* 播放联动
* 视图切换
* 节点跳转与导出

### 8.2 核心原则

* 模型负责理解，不直接控制绘图逻辑
* 前端 renderer 负责显示，不依赖特定模型输出风格
* 图形是中间结构的“不同视图”，不是独立产物

## 9. 核心技术路线：中间结构（Semantic IR）设计

### 9.1 设计目标

这里的“语义图谱层”不指庞大的知识图谱系统，而是一个**统一的中间结构协议**。
它的作用是把：

* 上游的转写/LLM 抽取结果
* 下游的各种图形 renderer

解耦开来。

### 9.2 为什么必须有中间结构

如果让模型直接输出某一种图代码，会有几个问题：

* 每种图都要单独写 prompt
* 同一内容难以切换不同视图
* 无法稳定支持节点跳转、speaker 过滤、导出等交互
* 很难做结构合并与后处理
* 维护成本会随图类型数快速上升

因此 Listen Graphic 的核心不是“模型直接画图”，而是：

> **模型输出统一结构，图形只是对统一结构的不同渲染。**

### 9.3 MVP 阶段最小中间结构

第一版只需包含：

#### 节点（Nodes）

节点类型建议先收敛为 5 种：

* `claim`：观点
* `reason`：原因/论据
* `example`：例子
* `question`：问题
* `conclusion`：结论

#### 关系（Edges）

边类型建议先收敛为 5 种：

* `supports`：支持
* `opposes`：反对
* `causes`：导致/因果
* `follows`：先后/步骤/时间推进
* `example_of`：举例说明

#### 元信息（Meta）

* `speaker`
* `timestamp`
* `confidence`
* `topic`
* `segment_id`

### 9.4 示例结构

```json
{
  "segment_id": "seg_001",
  "start_time": 125.4,
  "end_time": 178.2,
  "topic": "AI 创业公司为什么难盈利",
  "nodes": [
    {
      "id": "n1",
      "type": "claim",
      "text": "大模型公司很难靠 API 获得稳定利润",
      "speaker": "host",
      "timestamp": 130.2,
      "confidence": 0.88
    },
    {
      "id": "n2",
      "type": "reason",
      "text": "推理成本高，价格竞争激烈",
      "speaker": "guest_1",
      "timestamp": 141.6,
      "confidence": 0.84
    }
  ],
  "edges": [
    {
      "source": "n2",
      "target": "n1",
      "type": "supports",
      "confidence": 0.82
    }
  ]
}
```

### 9.5 第一阶段实现方式

第一版无需引入复杂图数据库。
只需：

* 定义固定 schema
* 让模型按 schema 输出严格 JSON
* 用简单 merge 逻辑拼接连续 chunk 结果
* 由前端根据 JSON 选择视图并渲染

## 10. 视图系统设计

### 10.1 MVP 阶段建议只做 4-5 种视图

不建议一开始就覆盖 10-15 种逻辑范式。
第一阶段优先支持下列高覆盖率视图：

1. **时间线视图**
2. **因果链视图**
3. **对比/辩论视图**
4. **步骤流程视图**
5. **层级框架视图**

### 10.2 视图与关系的映射

#### 时间线视图

适用于：

* 人物经历
* 项目发展
* 事件复盘
* 历史叙事

主要依赖：

* `timestamp`
* `follows`

#### 因果链视图

适用于：

* 问题拆解
* 原因分析
* 方案推演

主要依赖：

* `causes`
* `supports`

#### 对比/辩论视图

适用于：

* 正反讨论
* 多方观点冲突
* 观点共识/分歧

主要依赖：

* `claim`
* `opposes`
* `supports`
* `speaker`

#### 步骤流程视图

适用于：

* 方法论分享
* 操作步骤
* 落地指南

主要依赖：

* `follows`
* `conclusion`

#### 层级框架视图

适用于：

* 分类式讲解
* 知识体系整理
* 概念分层

主要依赖：

* `claim`
* `reason`
* `example`

### 10.3 自动匹配 + 用户切换

第一阶段可采用简单规则进行默认视图选择：

* `causes` 占比高 → 默认因果图
* `opposes` 边明显 → 默认对比图
* `follows` 边明显 → 默认时间线/流程图
* 否则 → 默认层级框架图

同时保留用户手动切换入口。

## 11. “实时”策略：从准实时开始，而非强实时

### 11.1 为什么不追求第一天就强实时

“实时生成”听起来最有吸引力，但也是最容易破坏体验的部分。
若同时追求：

* 低延迟 ASR
* 说话人分离
* 逻辑关系抽取
* 图形更新
* 播放联动

极易出现：

* 节点频繁重排
* 结构反复修改
* 说话人识别不稳定
* 图形跳动
* 用户认知负担增加

因此，第一阶段应优先实现：

> **准实时更新，而不是逐句强实时。**

### 11.2 三档更新策略

#### P0：听后生成

上传音频/导入已播节目后生成完整结构图。
用于验证“图有无价值”。

#### P1：准实时

每 30-90 秒为一个 chunk，增量更新结构。
适用于 MVP 与第一阶段产品。

#### P2：强实时

更细粒度的逐句高亮和动态节点展开。
作为后续优化方向。

### 11.3 图谱稳定层（必须补）

为了避免图形持续抖动，产品需要加入“稳定层”：

* 节点分为 `draft` 和 `confirmed`
* 新节点先以草稿态出现
* 达到置信阈值或 topic segment 结束后才固化
* 已固化节点尽量不重命名、不大幅改位置
* 大规模结构调整只在章节切换时发生

这会显著提升可读性和信任感。

## 12. 音频理解与 ASR 路线

### 12.1 核心原则

ASR 不是产品的核心壁垒，核心壁垒在于：

* 长音频结构化理解
* 统一中间表示
* 视图映射与收听交互体验

因此 ASR 采用“集成优先”而非自研。

### 12.2 支持的两种模式

#### 模式 A：本地优先模式

适合：

* 隐私敏感用户
* 技术型用户
* 希望低成本使用的用户

可选方案：

* Whisper / whisper.cpp / Faster Whisper 类本地转写方案
* 本地或轻量说话人识别模块

优点：

* 音频不出本地
* 成本可控
* 更符合“工具型产品”定位

#### 模式 B：托管增强模式

适合：

* 希望开箱即用的用户
* 对准确率要求更高的用户
* 不愿配置本地模型/环境的用户

方式：

* 接入商用转写服务
* 提供默认能力与高级套餐
* 用户可选择自带 API Key 或使用平台额度

### 12.3 说话人能力策略

MVP 阶段对 speaker 的要求不应过高。
建议先实现：

* 基础 speaker 标记
* 2-3 人播客的基本区分
* speaker 过滤能力

不建议第一版追求复杂多嘉宾高精度 speaker UX。

## 13. 模型调用与 Tool 设计原则

### 13.1 不让模型直接控制显示逻辑

产品的核心原则：

* LLM 负责结构抽取
* Tool/Renderer 负责视图渲染
* 视图逻辑由产品内部掌控

模型不直接输出某种图形代码，而是按约定输出统一 JSON。

### 13.2 Tools / Skills / Prompt 的合理职责

#### Prompt / Skill

负责：

* 从 chunk transcript 中抽取节点与关系
* 对结构进行标准化
* 按 schema 输出 JSON

#### Tool / Renderer

负责：

* 根据 JSON 渲染不同视图
* 控制样式、节点层级、交互规则
* 管理时间戳跳转和高亮

#### Merge / Post-process

负责：

* 跨 chunk 合并重复节点
* 去重与置信度更新
* 节点稳定化处理

### 13.3 合理的工程哲学

不是“多加一层大工程”，而是加一层**统一输出协议**。
这层协议越早定义，后面：

* 换模型越容易
* 换图类型越容易
* 加导出能力越容易
* 做交互越稳定

## 14. MVP 范围设计（4 周可验证版）

### 14.1 MVP 核心目标

MVP 要验证的不是“能不能把所有工程都做出来”，而是：

> **用户是否真的愿意用“结构化侧栏”替代纯字幕/纯摘要来理解长音频。**

### 14.2 MVP 保留项

第一版只保留：

1. 输入一集播客（本地文件或网页音频）
2. 生成 chunk 级结构图
3. 支持 3-5 种核心视图
4. 点击节点跳转对应时间戳
5. 基础 speaker 标记
6. 导出 Markdown / PNG / JSON

### 14.3 MVP 暂不做

第一版不建议强做：

* 全量逐句强实时
* 复杂多说话人精细可视化
* 太多图类型
* 深度平台合作
* 多平台深度导出集成
* 重型知识库闭环
* 复杂账号系统与分享系统

---

## 15. 4 周落地计划（重构版）

### 第 1 周：验证“内容能否稳定变成结构”

目标：

* 跑通音频 → transcript → 中间结构 JSON
* 定义 schema
* 完成 3 种基础 renderer（建议：因果图、对比图、时间线）

任务：

* 明确节点/边类型
* 编写 JSON 输出 prompt
* 处理静态音频样本
* 人工检查抽取质量

### 第 2 周：验证“结构是否真的帮助理解”

目标：

* 做最小 Web Demo
* 左侧文本/音频，右侧结构图
* 节点可点击回跳

任务：

* 实现前端 Demo
* 设计节点卡片/图面样式
* 完成默认视图选择逻辑
* 选取 5-10 条节目进行可用性测试

### 第 3 周：验证“准实时”是否可用

目标：

* 按 chunk 增量更新结构
* 引入初步稳定层

任务：

* 每 30-60 秒刷新一次
* 实现 draft / confirmed 节点机制
* 加入基础 speaker 标记
* 观察图抖动和用户感知

### 第 4 周：决定是否进入插件形态

目标：

* 基于反馈判断是否需要做 Chrome/Edge 插件

任务：

* 如果“边听边看”的使用率高，则进入 side panel 版本
* 如果“听后复盘”的价值更高，则继续强化 Web 版与导出能力

## 16. 用户体验设计重点

### 16.1 核心体验原则

* 图不要比内容更吵
* 更新不要打断收听
* 结构要稳定，不频繁重排
* 节点文本要短而清晰
* 交互要轻，不制造复杂操作负担

### 16.2 关键交互能力

#### 节点跳转

点击任一节点，播放器跳转到对应时间点。

#### 当前节点高亮

音频播放到对应段落时，高亮图中节点。

#### 视图切换

支持在同一段内容上切换为时间线/因果图/对比图。

#### speaker 过滤

只看主持人 / 嘉宾 A / 嘉宾 B 的观点。

#### 层级展开收起

只看核心结论，或展开论据和例子。

## 17. 数据与效果评估

### 17.1 MVP 成功不看什么

MVP 阶段不应只看：

* 总使用时长
* 生成时长
* 用户数

因为这些不能说明结构化视图是否真有价值。

### 17.2 MVP 最关键的验证指标

#### 1）结构图打开率

有多少用户在播放时实际展开并查看结构侧栏。

#### 2）节点点击率

有多少用户通过节点回跳时间戳，而不是仅把图当摆设。

#### 3）视图切换率

用户是否愿意在不同视图间切换，说明结构确实有可读价值。

#### 4）保存/导出率

听完后用户是否愿意保存图或导出内容。

#### 5）复访使用率

用户是否会在第二次听新节目时继续启用此功能。

#### 6）替代率

用户是否因为该功能而减少：

* 回拖音频次数
* 反复看逐字稿次数
* 手工记笔记次数

### 17.3 质量评估指标

技术侧建议补充：

* 节点抽取准确率
* 关系识别准确率
* speaker 准确率
* 默认视图匹配满意度
* 图抖动率
* 节点稳定率

## 18. 商业模式与成本策略

### 18.1 核心问题

这个产品天然会面临两个成本源：

* ASR 成本
* 结构抽取/大模型推理成本

如果完全由平台承担，免费模式会很重。
因此必须尽早明确成本策略。

### 18.2 双模式商业化建议

#### A. 本地模式

适合技术用户：

* 本地转写
* 本地/自带模型
* 一次性买断或轻订阅
* 强调隐私和自主可控

#### B. 托管模式

适合大众用户：

* 开箱即用
* 按时长/积分/订阅收费
* 可提供免费试用额度
* 高级用户可切换自带 API Key

### 18.3 为什么不能只做“用户自带 Key”

虽然自带 Key 对创业初期很友好，但问题是：

* 使用门槛高
* 非技术用户转化差
* 配置成本大
* 很难形成更广泛冷启动

因此建议将“自带 Key”作为高级能力，而非唯一入口。

## 19. 合规与版权策略

### 19.1 必须正视的问题

播客内容涉及：

* 平台分发权
* 创作者版权
* 内容抓取和处理边界
* 是否允许转录/再加工/商用

产品不能默认认为“只是做工具”就天然安全。

### 19.2 两种运行模式设计

#### Personal Mode（个人辅助理解模式）

* 用户对自己正在收听或本地拥有的内容进行个人理解辅助
* 结果默认不公开分发
* 优先本地处理
* 不沉淀为公共内容库

#### Creator Mode（创作者授权模式）

* 与创作者/节目方合作
* 可公开展示结构图
* 可嵌入节目页
* 可做更深分发与分享

### 19.3 MVP 阶段建议

第一阶段优先采用 **Personal Mode**。
避免一开始就进入：

* 公共抓取
* 批量生成公共结构页
* 聚合式内容库建设

这样能显著降低合规复杂度。

## 20. 风险与挑战

### 20.1 产品风险

* 大众用户未必愿意边听边看
* 图形表达可能对部分用户形成额外认知负担
* 高价值场景可能集中在少数深度用户

### 20.2 技术风险

* speaker 不稳定
* 结构抽取偏差
* 图持续抖动
* 内容跨 chunk 合并困难

### 20.3 商业风险

* 托管成本高
* 免费模式难以跑通
* 自带 Key 模式门槛高

### 20.4 竞争风险

已有产品会覆盖：

* 转写
* 摘要
* 时间戳导航
* 基础脑图生成

因此 Listen Graphic 不能只做这些能力，而必须在：

* 播客场景适配
* 多视图表达
* 收听联动交互
* 结构稳定性

上建立差异。

## 21. 护城河判断

### 21.1 真正的护城河不是什么

不是“会调用某个大模型”。
不是“能生成某种图”。
也不是“做了 ASR 集成”。

### 21.2 真正的护城河是什么

1. **中文长音频场景的结构抽取经验与数据**
2. **统一中间结构协议**
3. **内容语义到视图映射的规则与效果**
4. **播放器联动 + 节点交互 + 稳定更新的整体体验**
5. **面向播客访谈场景的持续优化**

也就是说，护城河来自：

> **语义抽取质量 + 视图匹配质量 + 使用体验积累**

而不是单点功能。

## 22. 中长期演进路线

### 阶段 1：验证价值

* 静态/准实时 Web Demo
* 核心视图 3-5 个

### 阶段 2：插件化

* Chrome/Edge side panel

* 创作者授权页
* 节目可嵌入结构图

### 阶段 5：知识工作流整合

* 更丰富导出

* “听后结构化复盘”的完整闭环

## 23. 结论

Listen Graphic 的机会不在于“再做一个音频摘要工具”，而在于：

> **把长音频从“只能顺着听”的线性媒介，变成“可以边听边理解、边看边导航”的结构化媒介。**

这个方向有真实痛点，也有足够明确的产品切入口。
但成功的关键不在于一开始就堆满“实时、多图、插件、平台合作”，而在于：

1. **先验证结构化视图本身有没有价值**
2. **用统一中间结构打通理解与显示**
3. **从准实时开始，优先保证稳定性**
4. **聚焦高价值播客场景，而非贪大求全**
5. **把产品做成“结构化收听层”，而不是 another transcript tool**

最终，Listen Graphic 应该成为的不是一个“生成图的小工具”，而是：

> **长音频内容的结构化界面。**
