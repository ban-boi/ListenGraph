# Listen Graphic 技术方案 v1

## 1. 先给结论：我建议你用这套

### 现在做插件 / Web Demo 时

我推荐你先用这一套：

* **前端**：TypeScript + React + Vite
* **插件形态**：Chrome Extension Manifest V3
* **UI 容器**：`sidePanel` + service worker + `offscreen document`
* **音频链路**：`tabCapture` + Web Audio API + AudioWorklet
* **本地存储**：IndexedDB
* **图形主引擎**：React Flow
* **自动布局**：dagre
* **导出层 / 文本图层**：Mermaid
* **统计/图表补充**：ECharts
* **数据协议**：统一中间结构 JSON（你前面认可的 semantic IR）
* **AI 接入方式**：Provider Adapter（ASR/LLM 都抽象成可替换 provider）
* **V0 后端**：可以不做，先本地 + 用户自带 Key
* **V1 后端**：再补 Python FastAPI 做托管 AI 网关

这套的核心逻辑是：

> **插件 / Web / 桌面尽量共用一套 React Web 前端和领域层；移动端不要硬共 UI，只共 schema、解析、provider、渲染规则。**

---

## 2. 为什么插件第一阶段适合这样做

Chrome 的 `sidePanel` 很适合你这个产品，因为它就是给扩展提供一个**持续存在的侧边栏 UI**，非常适合“边播边看”的伴随体验。`tabCapture` 可以在**用户触发扩展后**捕获当前标签页的音频流；而 `offscreen` 文档则正好用来解决 MV3 service worker 没有 DOM 的限制。Chrome 官方文档就是按这个思路提供这些能力的。([Chrome for Developers][1])

所以你第一阶段做插件，不用自己发明奇怪容器，直接走：

* sidePanel：承载主 UI
* service worker：承载扩展生命周期、消息分发、权限协调
* offscreen：做音频处理 / DOM 相关工作
* content script：只在需要和页面播放器做桥接时才加

这是比较正的架构。

## 3. 我对整体技术架构的建议

我建议你把整个系统拆成 5 层，而不是一坨前端逻辑。

### A. Shell 层

就是不同运行容器：

* 浏览器插件
* Web Demo
* 桌面客户端
* 移动端 App

### B. Domain 层

真正核心的产品能力，尽量跨平台共用：

* schema（中间结构）
* segment / chunk 逻辑
* merge 逻辑
* topic segmentation
* 视图选择规则
* 节点稳定层
* renderer 输入协议

### C. AI Provider 层

把 ASR / LLM 都做成适配器：

* OpenAI adapter
* Gemini adapter
* 通义 adapter
* 豆包 adapter
* Whisper local adapter
* Hosted adapter

### D. Render 层

负责把统一 JSON 渲染成不同图：

* 因果图
* 对比图
* 时间线
* 步骤图
* 层级图

### E. Storage 层

负责：

* transcript chunk
* segment graph
* 用户偏好
* provider 配置
* 导出缓存

这样做的好处是：
以后你换模型、换平台、换图形库，都不至于整套推倒。

## 4. 前端主栈：为什么我建议 TypeScript + React + Vite

这个部分我不讲套话，直接讲你这个项目为什么适合。

### 我推荐：

* **TypeScript**：必须
* **React**：必须
* **Vite**：推荐
* **Tailwind / 你熟悉的 UI 方案**：都可以
* **状态管理**：Zustand 或 Jotai 这种轻量方案
* **数据校验**：Zod

### 原因

你的核心前端不是“普通页面”，而是：

* 侧边栏常驻 UI
* 节点图交互
* 音频状态联动
* 多视图切换
* provider 配置
* 本地缓存与回放

这类产品本质上更像一个**小型前端工作台**，React 处理这种状态拼装会比轻模板方案舒服很多。

Vite 这里的价值是：
先做 Web Demo、再做扩展 UI、再塞进 Tauri，前端打包方式都比较顺手。这个是工程效率上的判断。

## 5. 浏览器插件端的推荐实现

## 5.1 插件架构

建议 Manifest V3，目录大概这样：

```text
apps/extension
  src/
    sidepanel/
    service-worker/
    offscreen/
    content-script/
    options/
```

### sidepanel

放主应用 UI：

* 播放状态
* 当前结构图
* 节点列表
* 视图切换
* provider 配置
* 导出功能

### service worker

负责：

* 插件启动
* 消息总线
* tab 状态
* 创建 offscreen 文档
* 权限与 session 生命周期管理

### offscreen document

官方就是给扩展提供一个**隐藏文档**去使用 DOM API 的；这在 MV3 下很重要，因为 service worker 本身没有 DOM，某些页面 CSP 也会限制 content script。([Chrome for Developers][2])

这个层我建议拿来做：

* 音频流接收
* AudioContext / AudioWorklet
* 分帧 / 重采样
* 本地 VAD
* 转录前预处理

### content script

只做很薄的一层：

* 读取播放器 DOM 状态
* 注入按钮
* 捕获页面里的播放时间
* 和 sidepanel 同步

不要把业务逻辑放 content script 里。

---

## 5.2 音频获取方案

第一阶段插件里最正的路线是：

1. 用户点击扩展按钮 / 启动监听
2. 用 `tabCapture` 抓当前 tab 音频
3. 把音频流送到 offscreen document
4. 在 offscreen 里做 AudioWorklet / chunking
5. chunk 发给 ASR provider

Chrome 官方明确说了 `tabCapture` 只能在**用户调用扩展之后**使用，这个约束你要从设计上接受，不要幻想静默抓网页音频。([Chrome for Developers][3])

---

## 5.3 音频处理方案

Web Audio API 适合做浏览器端音频处理；`AudioWorklet` 运行在单独的音频线程，适合做低延迟处理。MDN 也明确写了它适合低延迟、自定义音频处理。([MDN Web Docs][4])

所以推荐：

* **AudioWorklet**：主方案
  用于重采样、分帧、音量检测、轻量 VAD 前处理
* **MediaRecorder**：辅助方案
  适合调试、回放、保存原始 chunk；它对 `MediaStream` 录制很方便，但不是你实时链路的主干。([MDN Web Docs][5])

### 这里我替你把关一句

**第一版不要在插件里上太重的本地 ASR。**

虽然 WebAssembly 在现代浏览器里可运行、接近原生性能，而且可以和 Worker/模块组合使用；理论上在浏览器跑本地模型是可行的。([MDN Web Docs][6])
但对你这个项目来说，插件第一版如果直接做：

* 本地 whisper wasm
* 本地 diarization
* 实时图生成

会明显把复杂度拉爆。

### 更务实的建议

插件 V0：

* 浏览器端只做采集和轻处理
* ASR 先走远端 provider
* 结构抽取走远端 LLM
* 本地只做缓存和渲染

桌面端再考虑本地 whisper / whisper.cpp / Rust 推理桥。

## 6. 数据层怎么设计

## 6.1 本地存储

浏览器里我建议你把**会话数据**放 IndexedDB。
MDN 明确把 IndexedDB 定位成适合存大量结构化数据、文件 / blob，并支持离线场景。这个非常适合你存：

* transcript chunk
* audio chunk 元数据
* graph JSON
* 导出结果
* 会话历史([MDN Web Docs][7])

### 具体分法

* `settings`：用户配置、默认视图、provider 选择
* `sessions`：每一集播客的一次收听会话
* `chunks`：ASR chunk 和时间戳
* `graphs`：segment graph / merged graph
* `exports`：md/png/json 的缓存

### 不建议

不要把大量业务结构都塞进 `chrome.storage.sync` 这类扩展设置存储里。
它更适合小配置，不适合你这种音频/图结构数据。

这个你前面已经认了，我就直接给工程落法：

建议单独做一个包：

```text
packages/schema
```

里面放：

* `NodeType`
* `EdgeType`
* `SegmentGraph`
* `MergedGraph`
* `RendererInput`
* `ProviderOutput`
* zod schema / json schema

你之后所有平台都用这个包。

## 7. AI 层怎么做，才不会后期烂掉

## 7.1 Provider Adapter 一定要提前做

不要在代码里直接到处写 OpenAI / Gemini / 通义 SDK 调用。
你从第一天就应该抽接口。

### 推荐接口

```ts
interface AsrProvider {
  transcribeChunk(input: AudioChunk): Promise<TranscriptChunk>
}

interface LlmStructurer {
  extractGraph(input: TranscriptWindow): Promise<SegmentGraph>
}

interface DiarizationProvider {
  labelSpeakers?(input: AudioChunk | TranscriptChunk[]): Promise<SpeakerLabels>
}
```

### 为什么要这样

因为你后面一定会经历这几种变化：

* 用户自带 Key
* 你自己托管
* 不同模型做不同环节
* 浏览器插件和桌面端用不同 provider
* 国内外 provider 切换

如果不抽接口，后面一定是一锅粥。

---

## 7.2 我建议的 AI 路线

### V0

* ASR：远端 provider
* Structuring：远端 LLM
* Speaker：先弱化，可选

### V1

* 增加 chunk merge
* 规则选图
* 简单 speaker filtering

### V2

* 桌面端尝试本地 ASR
* 部分逻辑规则本地化
* 低成本 provider fallback

### V3

* 再考虑本地模型 / Rust bridge / on-device inference

## 8. 可视化组件到底怎么选

这块最关键，我直接给你结论：

## 主推荐：React Flow

React Flow 官方定位就是做**node-based UIs 和 interactive diagrams**，`<ReactFlow />` 本身就负责节点、边和交互管理，非常适合你这种“节点图 + 点击回跳 + 状态高亮 + 多视图切换”的产品。([React Flow][8])

### 为什么我推荐它做主画布

因为你的图不是静态图，而是要支持：

* 当前节点高亮
* 点击节点跳音频
* 按 speaker 过滤
* 局部展开/折叠
* 节点 hover 显示证据
* draft / confirmed 状态切换

Mermaid 很难优雅承接这类强交互。

### 配合什么布局

React Flow 文档里提到 dagre 很适合做 directed graph / tree 的布局，而且偏速度导向；对你 MVP 很合适。([React Flow][9])

所以我的建议是：

* **渲染层**：React Flow
* **布局层**：dagre
* **节点样式**：你自定义 React 组件

---

## 辅助推荐：Mermaid

Mermaid 是文本定义图的工具，支持 flowchart、timeline、mindmap、sequence、architecture 等多种语法。([Mermaid][10])

### 它适合干什么

我建议它做：

* 导出
* 分享
* 复制到文档/知识库
* debug 视图
* “轻量只读模式”

### 不建议它做什么

**不要拿 Mermaid 当主运行时交互画布。**

原因不是它不好，而是你这个产品需要的核心是：

* 实时局部更新
* 节点交互
* 局部高亮
* 自定义卡片节点
* 播放器联动

Mermaid 更像“文本到图”的表达层，不是“高交互图编辑/图工作台”的主引擎。

---

## 补充推荐：ECharts

Apache ECharts 提供很多图表类型，并支持 Canvas / SVG 渲染，适合补充统计面板和分析视图。([ECharts][11])

### 适合用在

* 节目结构概览
* speaker 占比
* 话题热度
* 节点密度随时间变化
* 时长 / 章节统计

### 不适合用在

* 主交互图画布

---

## 我不建议你现在主用 Cytoscape

Cytoscape.js 很强，偏复杂网络分析和可视化。([Cytoscape][12])
但你现在不是做“复杂网络分析平台”，而是做“收听中的结构化界面”。

所以现在上 Cytoscape 往往会：

* 学习成本更高
* 交互心智更偏 network graph
* 过度设计

除非你后面真要做“多人观点网络 / 节目知识图谱探索器”，否则 MVP 不用它做主。

## 10. 后面如果做桌面客户端，怎么走最稳

## 我的结论：桌面端选 Tauri 2

Tauri 2 官方明确支持你带着现有 web stack 去做桌面和移动端，并且支持 Windows、macOS、Linux，也支持 Android/iOS；应用逻辑可以下沉到 Rust，并可结合 Swift/Kotlin 做更深系统集成。([Tauri][13])

### 但我的建议是：

**你把 Tauri 当桌面优先，不要把它当移动优先。**

### 为什么桌面端适合 Tauri

因为你插件 / Web 第一阶段已经是 React Web 了。
这时候做桌面：

* 前端 UI 能高度复用
* 本地文件访问更方便
* 本地 ASR 更好接
* Rust bridge 能接本地推理 / 音频处理
* 导出、文件管理、缓存都比插件舒服

### 什么时候上桌面端

当你发现用户真的有这些需求时再上：

* 本地导入音频文件
* 本地长音频批处理
* 离线使用
* 本地模型/ASR
* 更稳定的性能

那时 Tauri 很合适。

## 11. 如果后面做移动端 App，别怎么做

## 我的结论：移动端别硬复用 React Web UI，直接 Expo / React Native

React Native 官方文档现在也明确建议通过 framework 来体验 RN；Expo 文档和 Expo Router 也强调它是做 Android / iOS / Web 的通用 RN 路线。([React Native][14])

### 所以移动端推荐：

* **Expo + React Native**
* **Expo Router**
* 共享 domain / schema / provider 层
* 不共享主 UI

### 为什么

因为移动端的核心问题不是“能不能显示图”，而是：

* 手势
* 小屏阅读
* 音频后台播放
* 前后台状态
* 节点展开方式
* 交互密度

这些和桌面/插件 UI 不是一回事。

### 你真正应该共享的是

* schema
* chunk / graph merge 逻辑
* provider adapters
* export mappers
* analytics event schema

### 不要硬共享的是

* React DOM UI
* 画布交互层
* 插件式状态机

## 14. 你现在最需要克制的几件事

### 1）不要一开始就做 Electron

你现在最强诉求不是“最快做出桌面壳”，而是：

* 插件先跑通
* Web 前端后面能复用
* 桌面端能接本地能力

这类产品我会优先看 Tauri，不会先上 Electron。

### 2）不要让 Mermaid 当主画布

Mermaid 做导出非常香，做主交互会卡你后腿。

### 3）不要为了“移动端以后也能用”而牺牲插件/Web 架构

先把插件和桌面这一条打顺。

### 4）不要过早做本地模型

浏览器插件第一版，别又搞本地 whisper、又搞 speaker、又搞 graph stability。

### 5）不要把 Key 管理想得太轻

API Key 如果走插件本地，一定要默认：

* 本地存储
* 用户可清除
* 不进 sync
* 明确提示风险

如果后面你做托管网关，再把真正的 secret 管理搬到服务端。
