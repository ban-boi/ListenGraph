# 扩展增量相机跟随

## 目的
本文记录 extension sidepanel 当前关于“图增量更新后，viewport 如何跟随”的产品决策与运行时约束。

这份文档关注的是：
- 为什么不能简单地对新增节点直接 `fitView`
- 当前实现为什么采用“聚焦 follow”而不是“保守 reveal”
- 当前相机跟随的目标区域如何计算
- 当前仍保留哪些保护规则与已知边界

## 背景
sidepanel 的图在一个 session 内默认被视为持续长出的阅读对象。

这意味着 viewport 的目标不是：
- 每次更新都重新 framing 全图
- 或者完全不动，始终停在最早的大视野

当前要解决的真实问题是：
- 早期宽图会把镜头拉得很远，后续局部增量会变得“能看见，但看不清”
- 如果直接 `fitView(updatedNodes)`，局部更新又容易把镜头吸进过小区域，失去上下文

因此当前 viewport 的原则从“尽量少动”调整为：

`在保持阅读上下文的前提下，主动聚焦当前刚更新出来的节点区域`

## 核心产品原则
### 1. 增量更新后允许系统重新聚焦
当前 sidepanel 在首帧之外，不再坚持“后续绝不动 viewport”。

当前行为：
- 首帧仍自动 `fitView` 一次
- 后续如果出现新增节点，系统会重新计算目标视口
- 目标是让用户更清楚地看见当前刚长出来的节点区域

当一次新增区域过长时，当前不再强求“一次镜头看完”，而是允许做多段自动导览。

### 2. 相机采用“聚焦 follow”，不是保守 reveal
当前不再只在“横向超出当前可视范围”时才缩小。

当前行为：
- 目标区域变宽时，允许 `zoom out`
- 目标区域变窄时，也允许 `zoom in`
- 只要当前 viewport 与目标 viewport 差得明显，就允许重新聚焦

这样做是为了避免：
- 早期宽图把镜头拉远后，后续长时间停留在“看不清”的尺度
- 用户虽然看见新增节点，但无法顺畅阅读其文本和结构

### 3. 动画比“变化小”更重要
当前不再限制单次缩放变化幅度。

当前原则是：
- 只要目标区域定义得正确，较大的缩放变化也是可以接受的
- 真正影响体感的不是“这次缩放大不大”，而是“目标对不对、过渡顺不顺”

因此当前实现选择：
- 用单段动画完成平移和缩放
- 不做“先平移、再缩放”的双段切换
- 不做人为的单次 zoom 变化钳制

### 4. 过长增量采用多段自动导览
当一次 struct 产出的新增区域过长、如果一次性装进视口会导致文字不可读时，当前会把这批新增内容拆成多段导览。

当前原则：
- 一次 struct 的新增内容最终要自动完整带看一遍
- 分段顺序按视觉主轴，从离锚点近到远推进
- 分段边界优先保持结构完整，不强求几何平均
- 每段都必须保持可读，且不能相对当前镜头突然缩得过多
- 导览结束后停在最后一段

## 目标区域规则
当前 viewport 跟随不是直接盯住“新增节点本身”，而是围绕一个目标区域计算。

### 1. 基础区域：新增节点包围盒
每次 `MERGED_GRAPH_UPDATED` 后，先识别本次新出现的节点 id。

当前行为：
- 对这些新增节点取最小外接矩形
- 这构成目标区域的几何核心

### 2. 上下文锚点：一跳旧邻居
如果新增节点通过边连接到已有旧节点，会把这些一跳旧邻居并入目标区域。

当前行为：
- 新增节点的 source / target 若是旧节点，则纳入锚点
- 只取一跳，不继续扩散

这样做是为了避免：
- 用户只看到一团新节点，却不知道它是从哪里长出来的

### 3. Padding 与最小上下文尺寸
目标区域在几何上会继续扩展：
- 外层加 padding
- 强制满足最小宽度
- 强制满足最小高度

这样做是为了避免：
- 局部更新时镜头缩得过紧
- 新增节点虽然看清了，但阅读上下文被裁得过狠

一句话概括：

`目标区域 = 新增节点包围盒 + 一跳锚点 + padding + 最小上下文尺寸`

### 4. 长条增量的分段规则
当新增区域过长时，当前不会直接对整批新增节点做一个总目标框，而是先切成多个 batch。

当前行为：
- 先按锚点距离和视觉主轴顺序排列新增节点
- 再按“还能否保持可读且平滑的缩放”逐步装入当前 batch
- 一旦继续装入会让当前 batch 低于可读阈值，或相对当前镜头缩得过多，就在此处分段
- 恢复导览时从下一段继续，而不是回播上一段

当前实现已经不再只使用单一的绝对缩放阈值，而是同时使用两层约束：

- 绝对可读阈值
  - 目标镜头再小也不能低于绝对可读底线
  - 当前参数：`AUTO_TOUR_ABSOLUTE_READABLE_ZOOM = 0.75`
- 相对缩放阈值
  - 即使目标镜头绝对上“还能读”，如果相对当前镜头突然缩小太多，也不允许并入同一段
  - 第一段允许稍微宽一点，因为它还要承担上下文建立
  - 当前参数：
    - `AUTO_TOUR_FIRST_BATCH_RELATIVE_RATIO = 0.8`
    - `AUTO_TOUR_RELATIVE_READABLE_RATIO = 0.85`

具体判断口径是：

- 第一段要求：`targetZoom >= max(0.75, currentZoom * 0.8)`
- 后续段要求：`targetZoom >= max(0.75, currentZoom * 0.85)`

这里的 `currentZoom` 不是始终拿导览开始前的那个 zoom，而是逐段推进：

- 第一段以导览启动前的当前 viewport 为基线
- 第二段开始，以前一段的目标 zoom 作为新的基线
- 因此后续段的“相对变化限制”是逐段生效的，不会出现第一段之后继续沿用旧基线的问题

这样做是为了同时满足两件事：

- 不让镜头缩到客观上难以阅读
- 不让镜头虽然仍可读，但一次性缩得太猛，导致体感突兀

一句话概括：

`当前分段不是“看到装不下就分”，而是“只要继续并入会破坏可读性或破坏平滑性，就提前分段”`

### 5. 第一段为什么更保守
当前第一段和后续段并不完全等价。

当前行为：
- 第一段在计算候选目标框时，会把锚点一起算进去
- 后续段默认只看该段新增节点，不强制继续携带锚点
- 第一段的相对缩放阈值比后续段更宽一点

这样设计的原因是：

- 第一段承担“建立上下文”的任务，需要告诉用户这批新增是从哪里长出来的
- 但第一段仍然不能为了带锚点而牺牲到不可读
- 后续段的目标则更纯粹：让用户逐段把新增内容读清

因此当前不是“第一段不做可读性判断”，而是：

- 第一段同样必须满足可读性约束
- 只是它的判断对象更大，且相对缩放规则略宽一点

当前选择的折中是：

- 第一段保上下文
- 后续段保阅读
- 如果二者冲突，优先继续分段，而不是继续缩小

## 运行时行为
### 1. 纯新增边不触发相机跟随
当前只有出现新增节点时，才会触发增量相机。

当前行为：
- 仅新增边：不动 viewport
- 无新增节点/边：不动 viewport

这样做是为了避免：
- 视觉上只是补了一条关系线，镜头却被系统抢走

### 2. 用户手动操作后进入冷却期
如果用户刚手动拖拽或缩放过画布，自动跟随会暂时让位。

当前行为：
- `onMoveStart` / `onMoveEnd` 会记录最近用户 viewport 操作时间
- 导览进行中若用户手动拖拽、缩放、点击节点或切换视图，导览会先暂停
- 若 3 秒内没有进一步交互，则自动从下一段恢复

这样做是为了避免：
- 用户正在自己找位置时，系统突然把镜头抢回去

### 3. 只在“已接近目标”时跳过
当前不会再因为“新增节点已经在视口内”就直接跳过。

当前行为：
- 先计算当前 viewport
- 再计算目标 viewport
- 只有当两者已经足够接近时，才认为这次无需动作

这意味着：
- 目标区域即使已经在当前画面里，只要还看得不够聚焦，系统仍会继续放大过去

### 4. 导览状态会显式提示
当前顶部状态区会显式提示自动导览状态。

当前行为：
- 导览中：绿色提示，显示“自动导览 x/y”
- 用户接管镜头后：切到暂停态，显示“导览暂停 x/y”
- 导览结束：恢复常规“运行中 / 空闲”状态

### 5. 单段停留时间是“中间偏快但能读”
当前每段导览的时间由两部分组成：

- 镜头移动动画
  - 当前参数：`AUTO_REVEAL_DURATION_MS = 320`
- 到位后的停留阅读窗口
  - 由节点数、边数、文本总字数共同估算

当前停留时间模型：

- `AUTO_TOUR_BASE_DWELL_MS = 900`
- `AUTO_TOUR_CHAR_DWELL_MS = 40`
- `AUTO_TOUR_NODE_DWELL_MS = 220`
- `AUTO_TOUR_EDGE_DWELL_MS = 90`
- `AUTO_TOUR_MIN_DWELL_MS = 1800`
- `AUTO_TOUR_MAX_DWELL_MS = 5000`

这组参数对应的产品语义不是：

- “扫一眼就切走”
- 也不是“按完整精读速度等待”

而是：

`中间偏快，但大多数用户已经有肉眼阅读当前一段主要信息的机会`

也因此，当前导览不是为了让用户在自动导览阶段完成完整深读，而是：

- 先把镜头带到正确位置
- 给用户一个真实可读的阅读窗口
- 再继续推进后续段

## 当前参数语义
当前实现里，相机手感主要由以下参数控制：

- `AUTO_REVEAL_PADDING`
  - 目标区域外扩的空白
- `AUTO_REVEAL_MIN_WIDTH_RATIO`
  - 目标区域的最小宽度，占当前可视宽度的比例
- `AUTO_REVEAL_MIN_HEIGHT_RATIO`
  - 目标区域的最小高度，占当前可视高度的比例
- `AUTO_REVEAL_DURATION_MS`
  - 单段 viewport 动画时长
- `USER_VIEWPORT_COOLDOWN_MS`
  - 用户手动操作后的自动跟随冷却窗口
- `AUTO_TOUR_RESUME_DELAY_MS`
  - 导览暂停后无进一步交互多久自动恢复
- `AUTO_TOUR_ABSOLUTE_READABLE_ZOOM`
  - 单段导览允许的最低绝对可读缩放阈值
- `AUTO_TOUR_FIRST_BATCH_RELATIVE_RATIO`
  - 第一段相对当前镜头允许的最小缩放比例
- `AUTO_TOUR_RELATIVE_READABLE_RATIO`
  - 后续段相对当前镜头允许的最小缩放比例
- `AUTO_TOUR_BASE_DWELL_MS / CHAR / NODE / EDGE / MIN / MAX`
  - 单段导览停留时间模型

如果后续要继续调手感，优先调这些参数，而不是重新改产品原则。

## 已知边界
当前实现仍有几个明确边界：

1. 目标区域仍基于稳定布局与固定卡片尺寸估算
- 当前不是基于真实 DOM 实测尺寸
- 文本极长、卡片实际高度变化大时，镜头 framing 仍可能略偏保守

2. 锚点只取一跳旧邻居
- 当前是刻意收敛
- 如果后续出现“用户仍看不懂新增节点挂在哪”的情况，再考虑扩大上下文范围

3. 当前仍没有单独的“恢复全图视角”产品入口
- 首帧之外，系统主要服务于增量阅读
- 如果后续用户需要频繁回到全图，可再补显式“重置视图 / fit all”入口
