# ListenGraph 多端产品路线

## 目的

本文记录 ListenGraph 接下来多端产品形态的路线判断，重点回答：
- 各端分别适合捕获什么声音
- 当前浏览器插件的产品定位
- 为什么下一步优先做桌面端
- 哪些能力应抽象为跨端共享，哪些必须按宿主分别实现

本文是当前产品路线说明，不属于 `docs/plans/` 下的自动生成参考文档。

## 产品输入模型

ListenGraph 后续所有端都围绕两类输入：

1. **设备内声音**
   - 浏览器标签页声音
   - 桌面系统外放声音
   - 其他应用播放的声音
   - 文件导入或历史录音导入

2. **外界实时声音**
   - 麦克风实时录音
   - 会议、课堂、线下对话
   - 手机或电脑作为现场听音设备

这两类输入在下游应统一进入同一条语义链路：

`AudioSource -> ASR -> Structurer -> Merge -> Graph -> UI`

不同端的差异主要集中在 `AudioSource`，不应扩散到图谱、结构化、合并和大部分 UI 层。

## 各端定位

### 浏览器插件

当前成熟形态是浏览器插件。它的主定位是：
- 抓取浏览器内的声音
- 监听网页、视频、网页会议、浏览器标签页里的音频内容
- 在侧栏中实时显示结构化图谱

当前主链路仍以 extension 能力为基础：

`sidepanel -> service-worker -> content-script -> getDisplayMedia -> AudioWorklet -> service-worker -> sidepanel`

因此浏览器插件不应被描述成“全设备声音捕获工具”。它更准确的产品定位是：

**浏览器声音专家。**

后续可以考虑为浏览器插件增加麦克风输入，但这不是它当前最重要的差异化能力。浏览器插件的优势是天然贴近网页内容和浏览器工作流。

### 桌面端

桌面端是下一阶段优先产品形态。它的主定位是：
- 抓取整个电脑的系统声音
- 抓取麦克风实时声音
- 后续支持系统声音和麦克风混音
- 复用现有图谱 UI、结构化逻辑、provider 配置和回归体系

桌面端是浏览器插件之后最自然的扩展，因为：
- 当前技术栈已经是 React + TypeScript + Web Audio 相关链路
- `packages/ui`、`packages/domain`、`packages/graph-renderers`、`packages/providers` 都有复用基础
- 桌面端能补上浏览器插件“只能稳定覆盖浏览器内声音”的产品短板
- 桌面使用场景和当前插件用户心智连续：用户仍然是在电脑上听内容，只是声音来源从浏览器扩大到整个系统

桌面端第一版不需要一次覆盖所有能力。推荐 MVP 顺序：

1. 建立桌面宿主应用和基础窗口
2. 复用现有图谱显示与 session UI
3. 支持麦克风输入
4. 支持系统声音输入
5. 支持系统声音与麦克风混音
6. 完善本地权限、设备选择、错误恢复和打包发布

### 手机 App

手机 App 的主定位是：
- 移动会议、课堂、线下对话的实时麦克风记录
- 移动端查看、回放和整理图谱
- 在平台允许范围内支持设备内声音捕获

手机端不应在早期承诺“稳定捕获整个手机所有系统声音”。平台能力不对称：
- Android 对系统内音频捕获更开放，但仍依赖系统授权和被捕获应用的策略
- iOS 对跨应用系统音频捕获更保守，适合优先做麦克风、导入、回放和查看体验

因此手机端建议晚于桌面端启动，且第一版应优先做：
- 麦克风实时输入
- 文件/文本导入
- 图谱查看与回放
- 与桌面/浏览器插件的数据同步或导出导入

### 网页端

网页端的主定位是：
- 轻量入口
- 演示与试用
- 图谱查看器
- 麦克风实时输入
- 文件、音频或文本导入

网页端的 UI 和图谱体验可以尽量接近桌面端，但音频捕获能力不能等同桌面 App。普通网页受浏览器权限模型限制，不应默认承诺稳定捕获整个设备的全部声音。

网页端可以作为跨端共享 UI 的验证场，也可以作为低门槛试用入口，但不应替代桌面端承担完整系统音频捕获能力。

## 技术抽象方向

后续实现多端时，应将音频输入明确抽象为宿主适配层：

```ts
interface AudioSource {
  start(): Promise<void>;
  stop(): Promise<void>;
  onAudioChunk(handler: (chunk: AudioChunk) => void): void;
  onStatus(handler: (status: AudioSourceStatus) => void): void;
}
```

候选实现：
- `BrowserTabAudioSource`
- `DesktopSystemAudioSource`
- `DesktopMicrophoneAudioSource`
- `MobileMicrophoneAudioSource`
- `FileAudioSource`
- `ReplayAudioSource`

下游链路应尽量保持一致：
- ASR provider
- stable utterance / transcript unit
- structurer
- merge / graph stability
- graph renderer
- timeline / logs / debug artifacts

## 当前优先级

当前路线排序：

1. **继续稳定浏览器插件**
   - 保持当前主链路可靠
   - 不急于把插件扩成全设备捕获
   - 继续把浏览器内声音场景做深

2. **启动桌面端**
   - 作为下一阶段重点
   - 先复用 UI 和业务链路
   - 再补桌面音频输入和权限能力

3. **保留网页端为轻量入口**
   - 不承担完整系统音频捕获承诺
   - 用于演示、查看、导入和部分实时麦克风能力

4. **手机端后置**
   - 优先定义为麦克风实时和移动查看
   - 系统内音频捕获按平台能力逐步增强

## 桌面端启动前的决策点

开始桌面端实现前，需要确认：

1. **桌面宿主技术选型**
   - Electron 更接近现有 Web 技术和音频/窗口生态
   - Tauri 更轻，但系统音频能力和插件工作量需要单独评估

2. **第一版音频输入范围**
   - 仅麦克风
   - 仅系统声音
   - 麦克风和系统声音二选一
   - 麦克风和系统声音混音

3. **运行时复用边界**
   - 哪些 service-worker 逻辑应抽到共享 runtime 包
   - 哪些 Chrome extension 消息与权限逻辑必须留在 extension 内

4. **数据与设置存储**
   - 桌面端是否继续复用 IndexedDB/Dexie
   - 是否需要本地文件导出、项目目录或账户同步

5. **发布目标**
   - 先 Windows
   - Windows + macOS
   - 是否需要 Linux

## 当前结论

ListenGraph 的跨端路线可行，但不应理解成“同一套网页技术直接获得所有平台的音频捕获能力”。

正确边界是：

**图谱、结构化、合并、provider 和大部分 UI 尽量跨端复用；音频采集层按浏览器插件、桌面端、网页端和手机端分别实现。**

因此，浏览器插件之后的下一步应优先做桌面端。桌面端最能延续当前产品场景，也最能补齐“设备内声音捕获”的关键能力。
