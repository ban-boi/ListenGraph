对，你理解得接近，但我把它说得太抽象了。这里分清两个东西：

**第二点是“语义质量验收”**：判断 LLM/assembler 抽出来的内容对不对。  
**第三点是“图形表达验收”**：判断同一份图数据画出来是不是清楚。

**第二点：结构化质量验收集是什么**
它本质上是一组“带答案标准的真实语音片段测试”。

不是普通单元测试那种精确到每个节点文本都必须一模一样，因为 LLM 输出天然会浮动。它更像一个半自动验收集：输入一段 transcript，跑当前 structurer，然后检查它有没有抓住关键意思。

一个 fixture 可以长这样：

```json
{
  "id": "problem-three-points-demo",
  "transcript": [
    "我觉得这个产品现在有三个问题。",
    "第一个是启动太慢，用户第一次打开会等很久。",
    "第二个是图出来以后有点乱，看不出重点。",
    "第三个是设置太复杂，新用户不知道该选哪个模型。"
  ],
  "expectations": {
    "mustContainTexts": ["三个问题", "启动太慢", "图有点乱", "设置太复杂"],
    "mustHaveNodeTypes": ["question", "claim", "reason"],
    "requiredEdgeTypes": ["supports"],
    "minMergedNodes": 4,
    "maxMergedNodes": 8,
    "maxFallbackNodes": 0,
    "forbiddenTexts": ["无关内容", "天气", "股票"]
  }
}
```

然后测试 runner 做这些事：

1. 把 transcript 喂给现有 service-worker/structurer 管线。
2. 得到 merged graph。
3. 自动检查：
   - 节点数是不是太少或太多。
   - 有没有关键文本。
   - 有没有关键边类型。
   - 有没有 fallback。
   - 有没有明显幻觉文本。
4. 生成报告：pass / fail / 需要人工看。

所以它是测试，但不是“死板快照测试”。它是“语义门槛测试”。

你现在项目里其实已经有类似机制，比如 `mustContainTexts`、`minMergedNodes`、`requiredEdgeTypes` 这些验收字段已经在 structure replay 体系里出现了。我的意思不是从零造一个新体系，而是把它升级成更贴近你产品目标的质量样本库。

“如果输入这种说法，系统至少应该抓住这几个点。抓不住，就不能说这版变好了。”

先不用 100 条。先做 20-30 条高价值真实片段，覆盖常见说话模式：

- 一个问题分几点讲
- 先说观点，再说理由
- 说着说着推翻前一句
- 插入口头禅、停顿、废话
- 举例说明
- 两个人争论
- 因果链
- 时间线叙述

这样你以后改 prompt、改 assembler、换模型，就能跑一遍，看是不是退步了。

**第三点：核心模式不是限制所有节点都只能套模板**
不是。

我不是说所有输出都必须套进 4-5 个模板。那样会把产品做死，变回你讨厌的传统思维导图。

我说的是：你要先保证最常见、最基本的表达模式能画清楚。

也就是：

自由图谱可以存在，但底层必须有几个稳定的“图形语法”。

比如“问题 -> 三个分点”这个模式，系统应该能画成：

```text
[问题：这个产品有三个问题]
        |
   ----------------
   |       |      |
[启动慢] [图乱] [设置复杂]
```

或者横向：

```text
[这个产品有三个问题] -> [启动慢]
                    -> [图乱]
                    -> [设置复杂]
```

这不是说所有图都必须这样，而是说：当数据里出现这种结构时，渲染器应该识别并优先用清楚的布局表达它。

**第三点的 graphic fixture 是什么**
它不是测 LLM。它不经过 ASR，也不经过 structurer。

它直接给一份固定 graph 数据，然后看布局和视觉表现。

比如：

```json
{
  "id": "layout-question-three-branches",
  "graph": {
    "nodes": [
      { "id": "q1", "type": "question", "text": "这个产品现在有哪些问题？" },
      { "id": "p1", "type": "claim", "text": "启动太慢" },
      { "id": "p2", "type": "claim", "text": "图谱太乱" },
      { "id": "p3", "type": "claim", "text": "设置复杂" }
    ],
    "edges": [
      { "source": "q1", "target": "p1", "type": "supports" },
      { "source": "q1", "target": "p2", "type": "supports" },
      { "source": "q1", "target": "p3", "type": "supports" }
    ]
  },
  "visualExpectations": {
    "rootNode": "q1",
    "branchNodes": ["p1", "p2", "p3"],
    "layout": "fanout",
    "noOverlap": true,
    "edgeHandlesReasonable": true
  }
}
```

然后测试或人工预览要回答：

- `q1` 是不是主节点？
- 三个分点是不是围绕它展开？
- 节点有没有重叠？
- 线有没有绕远？
- 自动聚焦后能不能读？
- 这张图一眼看起来是不是“一个问题分三点”？

这类 fixture 你仓库里已经有雏形：`packages/graph-fixtures` 和 `docs/testing/graph-layout-fixtures.md`。但现在的 fixture 更偏“增量增长、AutoFit、AutoTour”，还不够偏“语义图形模式”。

**第二点和第三点的关系**
同一个场景可以拆成两层验收。

比如场景：“一个问题分三点”。

第二层，结构化质量验收：

输入真实 transcript：

```text
我觉得这个项目现在有三个问题。第一是 UI 不统一，第二是图形逻辑不清楚，第三是代码结构还需要清理。
```

检查输出 graph 里有没有：

- “三个问题”
- “UI 不统一”
- “图形逻辑不清楚”
- “代码结构需要清理”
- 三个分点和主问题之间有关系

第三层，图形表达验收：

不管 graph 是 LLM 生成的还是手写的，只要 graph 里已经有：

```text
问题节点 -> 三个 claim 节点
```

那渲染器就必须画得清楚。

也就是说：

- 第二点回答：**有没有抽对？**
- 第三点回答：**抽对以后有没有画对？**

**具体落地顺序**
我建议你不要一下子做 30 条。先做一个最小闭环：

1. 选 5 条真实 transcript。
2. 每条写一个结构化 fixture。
3. 每条只写 3-5 个验收条件，不追求完美。
4. 跑现有 replay，看哪些失败。
5. 对其中 2 条手写对应 graph fixture。
6. 用 extension DEV fixture 或 web-demo 预览它们。
7. 观察图是否表达清楚。

第一批 5 条可以就选这些：

- 问题分三点
- 观点 + 理由 + 例子
- A 反对 B
- 因果链
- 说到一半修正前文

这五类如果能稳定跑通，项目质量会立刻从“能生成图”提升到“知道自己要生成什么图”。


- 主节点是不是看起来像主节点。
- 三个分支是不是形成分组。
- 支撑节点是不是挂在正确位置。
- 线是不是自然。
- AutoTour 是否按合理顺序带看。
- 一眼看上去是不是表达了“一个问题分三点”。

所以第三点最务实的落地方式就是：**复用你已有的 DEV fixture 机制，只是把 fixture 从“节点增长样本”升级成“语义模式样本”。**

它不需要先改很大架构。第一步就是新增 3-5 个 fixture JSON，然后用现在的 DEV 控制台观察。等模式稳定后，再把其中能自动断言的东西写进 Vitest，比如：

- 节点不重叠。
- root 节点位置在分支节点左侧或上方。
- 三个 branch 节点在同一层级。
- edge handle 不使用隐藏端点。
- 新增节点触发 auto-tour 分段。

人工判断负责“图像是否一眼可读”，自动测试负责“不退化到明显坏掉”。
